# Computer Control 0.2 Development Plan

This roadmap defines the `0.2` development line for an opt-in coordinate grid on screenshots. It is a focused usability feature for the existing screenshot-and-pointer workflow. It does not begin the separate desktop-isolation redesign on `v1.0` or change `main`'s `0.1.x` maintenance scope.

## Goal

Help an agent translate what it sees in a screenshot into the coordinates accepted by `pointer.*`, while keeping the image easy to inspect and leaving the user's visible desktop untouched.

## Proposed API

Add one optional boolean parameter to `screen.capture`:

| Parameter | Type | Default | Behavior |
| --- | --- | --- | --- |
| `show_grid` | boolean | `false` | Draw a coordinate grid and labels into the returned screenshot image. |

Example: `{"tool":"screen.capture","arguments":{"show_grid":true}}`.

The default remains `false`, so existing calls, visual output, and token cost stay unchanged. The option changes only the returned image; it does not draw a window or overlay on the physical desktop, move the pointer, change focus, or grant any new input permission. `screen.capture` remains a read-only action.

## Grid and coordinate contract

- Express every label in the same model-canvas coordinate system accepted by `pointer.move`, `pointer.click`, `pointer.drag`, and `pointer.scroll`. Do not label physical desktop pixels.
- For a full-desktop capture, the model canvas begins at `(0, 0)` over the virtual desktop, even when that desktop has a negative physical origin because of monitor arrangement.
- For a `region` capture, draw only grid lines that fall within the actual captured crop, but label them with their absolute model-canvas coordinates. A crop must not reset its top-left coordinate to `(0, 0)`.
- The current response describes the full canvas but does not report the resolved, clamped origin of a region crop. Additive response metadata such as `capture_region: {x, y, width, height}` must describe the actual captured bounds in model-canvas coordinates, so an agent can map a point in the cropped image back to a valid pointer coordinate. Compute it from the final clamped physical capture bounds, including the existing rounding behavior.
- Lay out grid lines and labels against the final returned frame dimensions after scaling and the configured area limit. The selected grid interval and label positions must remain accurate when `scale`, `region`, or the area limit changes the output size.
- Choose a readable interval automatically from a `1`, `2`, `5` progression by powers of ten, targeting roughly 6–12 major divisions across the visible crop. Keep this as one `show_grid` option for the first release; defer user-configurable spacing and colors until usage shows a need.
- Use thin, visually distinct lines and small labels with a contrasting background so UI controls and text remain visible. Place x labels along the top and y labels along the left edge; avoid covering the center of the captured content with coordinate text. Respect `grayscale=true` by rendering the grid in gray tones.
- When enabled, return additive metadata describing that the grid is present, its interval, and its coordinate space. Preserve the screenshot's width, height, requested PNG/JPEG format, quality, and grayscale behavior; encode the composed frame using the existing output settings.

## Implementation plan

1. **Lock the mapping contract.** Define and document `capture_region` for full and cropped frames, including off-canvas clamping, negative physical monitor origins, and rounding at physical-pixel boundaries.
2. **Add a shared image annotation helper.** Draw the grid after capture scaling/cropping and grayscale conversion but before final PNG/JPEG encoding. Use the existing Pillow dependency; keep the helper separate from desktop input and window management.
3. **Expose `show_grid`.** Add strict boolean validation, tool-schema text, returned grid metadata, and examples. Leave the default and the existing capture payload fields compatible.
4. **Document practical use.** Update the action guide and README with the option, its coordinate mapping, region behavior, and the fact that the annotation exists only in the returned image. Include a short example showing a labeled screenshot followed by `pointer.click` at the same canvas coordinates.
5. **Check representative outputs.** Review full-screen and cropped examples at multiple scales in PNG and JPEG, including grayscale and multi-monitor layouts. Check label readability, image-size overhead, and that the screenshot remains useful for visually locating controls.

## Acceptance criteria

- Omitting `show_grid` or setting it to `false` preserves the existing screenshot behavior and does not add grid pixels or grid metadata indicating an active grid.
- Setting `show_grid=true` adds a legible coordinate grid and labels to the returned image without changing its dimensions or requested format.
- Labels correspond to the same model-canvas coordinates accepted by pointer actions. This remains true after image scaling, area limiting, regional cropping, and physical-boundary clamping.
- A cropped frame reports its resolved canvas-space origin and size; its top-left image pixel is never mislabeled as global coordinate `(0, 0)` unless that is the actual captured origin.
- Grid rendering works with PNG, JPEG quality settings, grayscale captures, and multi-monitor virtual desktops, including negative physical monitor coordinates.
- No physical desktop overlay appears; capture does not activate a window, move the pointer, or send keyboard/mouse input.
- Invalid values for `show_grid` are rejected using the existing strict-argument behavior.
- Existing integrations that omit the new parameter continue to work with the current API defaults.

## Out of scope

- OCR, image recognition, or automatic detection of controls.
- Screen Search labels or accessibility-tree changes.
- A persistent overlay on the user's screen, focus changes, or pointer movement.
- User-configurable grid style/spacing in the first release.
- Desktop isolation, app attach/launch modes, or new operating-system drivers; those remain on the separate `v1.0` roadmap.

## Branch and tracking

- `v0.2` is the isolated development line for this feature. Its baseline is the current `main` maintenance head.
- Submit roadmap and implementation changes through short-lived branches and pull requests targeting `v0.2`; do not commit directly to the long-lived version branch.
- Track feature work and compatibility decisions through issues and pull requests linked to this roadmap. Keep `main`'s `0.1.x` maintenance line and the independent `v1.0` redesign separate.
