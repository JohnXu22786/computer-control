# Computer Control 0.2 Development Plan

This roadmap defines the `0.2` development line for an opt-in coordinate grid on screenshots. It is a focused usability feature for the existing screenshot-and-pointer workflow. It does not begin the separate desktop-isolation redesign on `v1.0` or change `main`'s `0.1.x` maintenance scope.

## Goal

Help an agent translate what it sees in a screenshot into the coordinates accepted by `pointer.*`, while keeping the image easy to inspect and leaving the user's visible desktop untouched.

## Proposed API

Add one optional boolean parameter to `screen.capture`:

| Parameter | Type | Default | Behavior |
| --- | --- | --- | --- |
| `show_grid` | boolean | `false` | Draw a coordinate grid and labels into the returned screenshot image. |

Example: `{"tool":"screen.capture","arguments":{"show_grid":true}}`.

The default remains `false`, so existing calls, visual output, and token cost stay unchanged. The option changes only the returned image; it does not draw a window or overlay on the physical desktop, move the pointer, change focus, or grant any new input permission. `screen.capture` remains a read-only action.

## Existing behavior and compatibility contract

Synchronize the `v0.2` baseline with `main` before implementation. Preserve the latest successful capture's action coordinate surface for `pointer.*`, including captures with `region` and `scale`; enabling the grid must not implicitly switch pointer actions to absolute desktop coordinates. Calls omitting `show_grid`, existing payload fields, capture behavior, and pointer mapping remain compatible. #137–#139 must verify the supported capture paths, including partial and wholly off-desktop regions, scaling, area limits, negative physical origins, and physical-pixel rounding. Report the bounds actually captured, including any full-desktop fallback; do not substitute the requested bounds.

A later successful capture can replace the active action surface. Coordinates read from an earlier frame can therefore point elsewhere after another capture. Callers should use the latest frame for pointer actions. This contract does not claim that stale-frame actions are rejected.

## Grid and coordinate contract

- **The grid follows the latest capture's action surface.** Its labels represent the coordinates consumed by the paired `pointer.*` action, including after cropping and scaling. A crop's action origin is relative to the captured surface, not the desktop's absolute origin. A supported app-specific provider must use its paired action frame and target; do not assume every app has local coordinates.
- Show the horizontal `x` axis and tick values along the top edge and the vertical `y` axis along the left edge; `x` increases rightward and `y` downward. Align ticks with grid lines and mark the active frame's origin as `(0, 0)` when visible. Distinguish the narrow axis-label bands from content and keep image dimensions unchanged.
- Add response metadata for the actual captured desktop bounds in physical pixels, the returned image dimensions, and the active action surface and its mapping to those bounds. Identify coordinate spaces and units explicitly; account for clamping, outward rounding, scaling, area limits and output-size rounding. The mapping must let a caller convert a returned image position to the corresponding pointer coordinate and physical desktop position. For app-local captures, use the provider's declared frame and target identity. Existing fields remain compatible.
- For a full-desktop capture, the action surface spans the combined virtual desktop; a negative physical monitor origin does not make the action origin negative. For a region capture, grid labels start in the latest capture's action frame, even when the actual physical crop begins elsewhere on the desktop.
- Lay out grid lines and labels against the final returned frame dimensions after scaling and the configured area limit. The selected grid interval and label positions must remain accurate when `scale`, `region`, or the area limit changes the output size.
- Choose a readable interval automatically from a `1`, `2`, `5` progression by powers of ten, targeting roughly 6–12 major divisions across the visible crop. Keep this as one `show_grid` option for the first release; defer user-configurable spacing and colors until usage shows a need.
- Use thin, visually distinct lines and small labels with a contrasting background so UI controls and text remain visible. Place x labels along the top and y labels along the left edge; avoid covering the center of the captured content with coordinate text. Respect `grayscale=true` by rendering the grid in gray tones.
- When enabled, return additive metadata describing that the grid is present, its interval, and its coordinate space. Preserve the screenshot's width, height, requested PNG/JPEG format, quality, and grayscale behavior; encode the composed frame using the existing output settings.

## Coordinate frame must match the action

The grid is a visualization of the coordinates that the next input action will consume. Do not add a user-facing `screen` versus `app` switch that can disagree with the active input tool. The capture result and action context must identify the coordinate-frame type and its target; when `show_grid=true`, the returned grid metadata must repeat that frame so the agent can check the match.

For the desktop route, labels use the latest capture-relative action surface, including for a crop. The metadata also describes where that surface maps onto the physical virtual desktop. If an app-specific provider later exposes paired app-local capture and input, it must declare the app/window identity, local origin and dimensions, and transforms for scaling/DPI or window changes; the grid follows that declared app frame only for actions sent through the same provider and target. If the capture and input frames are unknown or do not match, do not draw potentially misleading coordinates; return an explicit unsupported/mismatched-frame error.

App-local mapping also needs to define whether its origin includes title bars and other non-client regions, and how resize/move affects a live target. For v0.2, the desktop pointer route is the supported route. Any app-specific route is conditional on a provider proving its mapping and target behavior; v1 can evaluate such routes as part of its target/session design.

## Measurable mapping examples

These examples describe the required relationship, with exact dimensions chosen to avoid rounding ambiguity. The implementation must also test the actual rounding and clamping rules.

- Full desktop: physical bounds `(-1920, 0, 3840, 1080)` and a returned/action surface of `1920 × 540` map action `(0, 0)` to physical `(-1920, 0)` and `(960, 270)` to `(0, 540)`. Monitor boundaries do not restart the grid.
- Crop: actual physical bounds `(200, 100, 800, 400)` returned as `400 × 200`, with a matching `400 × 200` action surface, map image/action `(0, 0)` to physical `(200, 100)` and `(200, 100)` to physical `(600, 300)`. Labels use `(0, 0)` at the crop origin, not `(200, 100)`.
- If a subsequent capture changes the action surface, the same action coordinate is interpreted using that later surface. Metadata must report the resolved bounds and transforms for each capture, including partial crops and a full-desktop fallback where applicable.

## Implementation plan

1. **Lock the mapping contract.** Define and document actual capture bounds and mapping metadata for full and cropped frames, including off-canvas clamping, negative physical monitor origins, and rounding at physical-pixel boundaries.
2. **Add a shared image annotation helper.** Draw the grid after capture scaling/cropping and grayscale conversion but before final PNG/JPEG encoding. Use the existing Pillow dependency; keep the helper separate from desktop input and window management.
3. **Expose `show_grid`.** Add strict boolean validation, tool-schema text, returned grid metadata, and examples. Leave the default and the existing capture payload fields compatible.
4. **Document practical use.** Update the action guide and README with the option, its coordinate mapping, region behavior, and the fact that the annotation exists only in the returned image. Include a short example showing a labeled screenshot followed by `pointer.click` at the same canvas coordinates.
5. **Check representative outputs.** Review full-screen and cropped examples at multiple scales in PNG and JPEG, including grayscale and multi-monitor layouts. Check label readability, image-size overhead, and that the screenshot remains useful for visually locating controls.

## Visual acceptance examples

Review paired unannotated and annotated captures at the same output settings, retaining examples and encoded byte counts with the validation results (#149). The examples must show:

- Light and dark interfaces: lines and edge labels remain distinguishable on both, while controls and their text remain usable.
- Dense text and a small crop: labels stay in the edge bands, do not obscure the central content, and remain readable at the returned size. When there is insufficient room, reduce or omit overlapping labels rather than draw illegible text; retain truthful tick positions.
- Grayscale: grid and labels remain distinguishable in gray tones without introducing color, including in JPEG output.
- Label overlap: inspect large coordinate values and narrow dimensions; neighboring labels and the two axis bands do not collide or obscure one another.
- Image overhead: compare annotated and unannotated PNG and JPEG byte sizes on the same captures and report the increase alongside visual results, so the cost can be evaluated before acceptance.

## Acceptance criteria

- Omitting `show_grid` or setting it to `false` preserves the existing screenshot behavior and does not add grid pixels or grid metadata indicating an active grid.
- Setting `show_grid=true` adds a legible coordinate grid and labels to the returned image without changing its dimensions or requested format.
- Labels correspond to the same declared coordinate frame and target consumed by the paired input action. This remains true after image scaling, area limiting, regional cropping, and physical-boundary clamping.
- The `x` and `y` axes and tick labels appear at the top and left edges respectively; x increases rightward and y downward. On the desktop pointer route, labels use the latest capture-relative action surface, including for a crop or a capture spanning multiple monitors.
- If an app-local provider is supported, the capture and input action share the same app/window identity and declared local frame; unknown or mismatched frames fail clearly instead of showing misleading labels.
- A cropped frame reports its actual physical bounds and the image-to-action and action-to-physical mappings; its action origin is relative to the captured surface. A later capture can change that surface, and stale-frame rejection is not assumed.
- Grid rendering works with PNG, JPEG quality settings, grayscale captures, and multi-monitor virtual desktops, including negative physical monitor coordinates.
- No physical desktop overlay appears; capture does not activate a window, move the pointer, or send keyboard/mouse input.
- Invalid values for `show_grid` are rejected using the existing strict-argument behavior.
- Existing integrations that omit the new parameter continue to work with the current API defaults.

## Out of scope

- OCR, image recognition, or automatic detection of controls.
- Screen Search labels or accessibility-tree changes.
- A persistent overlay on the user's screen, focus changes, or pointer movement.
- User-configurable grid style/spacing in the first release.
- A manual coordinate-space selector independent of the capture/input target.
- Desktop isolation, app attach/launch modes, or new operating-system drivers; those remain on the separate `v1.0` roadmap.
