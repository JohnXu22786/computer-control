# Computer Control 0.1 Maintenance Plan

This roadmap tracks compatible maintenance for the current `0.1.x` line on `main`. The major desktop redesign is planned separately on `v1.0`; this document keeps the existing package useful and predictable while that work proceeds. Items below are planning priorities, not a release schedule or authorization to change defaults.

## Goal

Keep the current Windows desktop-control plugin reliable for existing integrations, make the result of an interrupted or timed-out action clear, and preserve the established action protocol.

## Current capabilities and behavior

- `screen.capture` returns a full-screen or regional screenshot.
- `pointer.click` accepts canvas coordinates; `pointer.move`, `pointer.drag`, and `pointer.scroll` also use coordinates.
- `a11y.snapshot`, `a11y.activate`, and `a11y.input` provide Windows UI Automation when available. Current `auto` activation and text input can fall back to pointer actions.
- Coordinate input acts on the current desktop through the Windows driver. It is not background-targeted or desktop-isolated and can affect the user's foreground desktop.
- No OCR or image-scanning subsystem is planned. Screenshots remain the visual context for the existing computer-use loop.

The screenshot-plus-coordinate interaction already exists in v0. It is not a new v1-only feature. v1 will add a different execution context for supported actions, described in the separate v1.0 roadmap.

## Maintenance priorities

1. **Report stop state accurately.** When `session.stop` reaches its wait limit while an action is still running, expose that the action remains in flight instead of reporting an unqualified `idle` result. Keep queued work blocked and make the final stopped state queryable.
2. **Make action timeouts reconcilable.** A caller timeout currently means the action may still complete later. Give each submitted action a stable identifier and queryable queued/running/completed/unknown outcome; cancel work that has not started where possible. Never imply that an in-flight hardware action was cancelled, and document that callers should not blindly retry an unknown result.
3. **Make accessibility fallback explicit.** Preserve the current `auto` behavior for compatibility, while offering a strict semantic-only mode and a configurable or confirmable coordinate fallback. Return the actual method used so callers can tell when a physical click occurred.
4. **Protect the protocol contract.** Add focused regression coverage and update action, lifecycle, and integration documentation for stop, timeout, retry, and fallback behavior. Keep existing action names and defaults unless a separately reviewed compatibility change is approved.

## Out of scope for v0.1 maintenance

- Desktop/session isolation, worker compositors, or new app attach/launch modes.
- macOS or Linux drivers, including Wayland support.
- A Screen Search label overlay or a new OCR/image-recognition path.
- A broad rewrite of the action protocol or silent changes to coordinate semantics.

These belong to the independent `v1.0` development line. The existing screenshot and coordinate tools may continue to be used by v0 integrations with their current foreground-desktop semantics.

## Completion checks

- Stop responses and status/events distinguish an idle session from a stop request with an action still in flight.
- A timed-out action has a documented, queryable outcome; queued work can be cancelled where safe, while running work is never reported as cancelled without evidence.
- Accessibility activation/input reports whether it used a semantic API or a coordinate fallback, and callers can select a semantic-only policy without changing the compatibility default.
- Existing clients retain the current action shapes and coordinate contract.
- Regression tests cover queue/running timeout and stop races, fallback selection, and compatibility behavior.

## Branch and tracking

- `main` remains the `0.1.x` maintenance line while `v1.0` develops independently.
- Submit each bounded maintenance change through a short-lived branch and pull request targeting `main`; do not mix v1 redesign work into this line.
- Link maintenance issues and pull requests to this roadmap. Any handoff of `main` to v1 requires a separately reviewed version handoff.
