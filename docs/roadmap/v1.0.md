# Computer Control 1.0 Development Plan

`v1.0` is the development and integration line for the Computer Control 1.0 redesign. This is a major desktop-control direction change. Work for this plan belongs to the `v1.0` line; the current `main` line is outside this plan until an explicit version handoff is agreed. This roadmap describes intended work, not a release date or a promise that every application exposes every capability.

## Goal

Let an agent operate the user's desktop applications with as little interruption as possible, while keeping the user in control of their current desktop, applications, data, and permissions.

The product must support both selecting an application that is already open and starting a new instance of an application already installed on the user's machine. These are separate ways to target an application and neither substitutes for the other.

## Scope and product rules

- Desktop operation only. Browser automation is outside this roadmap.
- Reuse applications already installed on the user's machine. Installing or provisioning a second application copy is not the default workflow.
- **Attach to an existing app:** select an eligible running app/window and bind actions to that exact process, window, and current document/session. Prefer semantic accessibility actions that do not activate the window. If an action needs foreground input, request an explicit, temporary handoff or return a clear refusal. Never silently steal focus.
- **Launch a new app instance:** start a separate, agent-owned instance from the user's existing installation in a worker session/compositor where supported. The user chooses whether profile, files, clipboard, and other data are shared. Detect single-instance forwarding and profile conflicts; do not claim that a host app window became isolated.
- Report whether an action used the existing live process, a new process from the same installation, or an attended foreground handoff. Report session/window identity, focus impact, capture source, and refusal reason.
- Focus isolation is distinct from data/security isolation. A same-machine worker may still share the user's account, files, network, and application data.
- No OCR or image-scanning subsystem for Screen Search. The existing computer-use screenshot path may continue to provide visual context.
- Screenshot observation and coordinate-based pointer actions are existing v0 capabilities and remain available as low-level primitives in v1. In v1, capture and coordinate input must be routed to the selected target context: the agent-owned worker for `launch_new`, or a verified target-scoped route for `attach_existing`. A global host screenshot/click path is not an implicit fallback for an isolated task. If an existing app requires foreground coordinates, request an explicit attended handoff or refuse. Coordinates are not Screen Search recognition; Screen Search remains semantic-only and adds no OCR or pixel scanning.
- Do not switch the user's active desktop or Space as an automation mechanism. If a supported background or worker route is unavailable, refuse or request an explicit attended handoff.

## Platform direction

| Platform | Attach to an existing app | Launch a new app | Known boundary |
| --- | --- | --- | --- |
| Windows | UI Automation (UIA) against the selected live window, only for controls verified to work without activation. | Evaluate a same-machine child/Picture-in-Picture session that uses existing installed apps. | App/session compatibility, authentication, single-instance behavior, and UIA support must be verified per app. A child session is focus separation, not a VM security boundary. |
| macOS | Accessibility (AX) against the selected live app/window, with per-action focus guarantees. | Add a worker desktop only if a same-host option proves it can avoid switching the visible desktop and reuse the user's app installation. | No general no-switch worker desktop has been established under these constraints. Do not make a guest VM or new app installation the default. |
| Linux | AT-SPI against the selected live app where supported by the desktop and app. | A nested/headless Wayland compositor launching native Wayland apps from the existing host installation. | Wayland only: no X11 or XWayland route. Qualify compositor/app support. Existing host windows cannot be assumed transferable. A nested compositor shares the host kernel. |

## Shared interaction model

The shared provider API will expose `target_mode=attach_existing|launch_new`, target and process identity, installation/profile/live-process reuse, session/display identity, available semantic actions, input and capture scope, focus impact, and structured refusal reasons such as `background_unavailable` and `foreground_required`. Screenshot capture and coordinate input must use that same target/session scope. Providers must not silently change the target mode or fall back to host-wide mouse/keyboard input.

For existing applications, actions bind to the selected live window and document. For new applications, the worker owns the launched process and its capture/input route. Any profile or data sharing is an explicit permission. If an app forwards a worker launch to an existing host process, the provider detects the mismatch and stops rather than treating the host process as worker-owned.

## Screen Search

Screen Search lists and selects semantic controls using Windows UIA, macOS AX, and Linux AT-SPI. It supports short-lived control labels and name/role search, and revalidates the target before activation. It does not use OCR, image recognition, or pixel scanning. A visual hint overlay is optional; when the agent operates in a worker, the overlay stays in that worker. A host overlay is shown only when the user invokes it.

## Permissions and user control

- Grant access by application and target mode; separately scope files, profile/data, clipboard, network, credentials, and administrative actions.
- Explain when an operation is focus-isolated but still has access to the user's account or data.
- Provide task status, pause, stop, optional read-only preview, and explicit takeover/release controls.
- Taking over pauses the agent first so user and agent input cannot race. Preview does not grant host input permission.
- Confirm high-impact actions such as sending, deleting, purchasing, payment, or changing security settings.

## Development milestones

1. **Define focus-safety guarantees.** Specify host focus, active desktop/Space, pointer and keyboard leakage, target identity, screenshot provenance, and the exact conditions for refusal or attended handoff. Unknown targets fail closed.
2. **Prove the reuse model on each platform.** Test attach-existing and launch-new separately. Verify same installation, live process, profile/data scope, authentication, single-instance forwarding, screenshots, and accessibility behavior before selecting each worker approach.
3. **Define the shared session/provider contract.** Expose target mode, process/window/session identity, capability, focus impact, resource scope, capture source, and refusal reason. Disallow implicit target-mode or foreground fallback.
4. **Deliver Windows support.** Add verified UIA actions for existing windows and a same-machine worker-session path for new instances where app compatibility is proven.
5. **Deliver macOS support.** Add AX actions for existing windows. Add a no-switch worker route for new instances only after it passes the same-installation and no-disturbance requirements; otherwise publish the exact unsupported cases.
6. **Deliver Wayland-only Linux support.** Add AT-SPI actions for existing apps and a nested native Wayland worker for new instances. Exclude X11 and XWayland and document supported compositors and applications.
7. **Add semantic Screen Search.** Provide UIA/AX/AT-SPI control selection and search with short-lived IDs and target revalidation; add no OCR/image scanning.
8. **Add permission and takeover controls.** Scope app/data access, disclose focus versus data isolation, and provide pause, stop, preview, and explicit handoff.
9. **Publish the compatibility and acceptance matrix.** Report, for each tested OS/compositor/app/action, whether the agent attached to the live process or launched a new one, whether it reused the installation/profile, focus and input isolation evidence, setup requirements, and known refusals.

## Acceptance criteria

- Both `attach_existing` and `launch_new` are represented in the user-facing target selection and the provider API on supported platforms.
- An attach-existing action remains bound to the selected running process/window/document. Semantic background actions leave host focus, active desktop, pointer, and keyboard ownership unchanged when advertised as no-focus.
- A launch-new worker uses the existing installation and has its own verified process/session/capture identity. Host input is not injected; single-instance forwarding and unsafe shared-profile conflicts fail closed.
- A screenshot and any following coordinate action refer to the same verified target/session. Worker actions do not inject into the host desktop; attach-existing coordinate actions require a verified target-scoped route or an explicit attended handoff.
- Focus-bound operations request an explicit attended handoff or return a structured refusal. There is no silent focus-steal fallback.
- Screen Search works through semantic accessibility controls only; no OCR or image scanner is added.
- Linux support is native Wayland only, with an explicit compositor/app support matrix and no X11/XWayland fallback.
- Permissions are task-scoped and revocable; preview, pause, stop, and takeover behavior are documented and verified.
- No platform is described as no-disturbance until concurrent user typing/mouse activity and host focus/input leakage have been checked on that platform.

## Research references

These projects are references for evaluation, not selected dependencies:

- [Cua Driver](https://github.com/trycua/cua) — MIT-licensed driver candidate for window-targeted background actions; support is platform, app, and compositor dependent. The separate [Cua Spaces macOS app](https://github.com/trycua/cua/blob/main/apps/cua-spaces-macos/LICENSE) uses FSL-1.1-MIT, not the driver's MIT license.
- [Vimdose](https://github.com/az-pz/vimdose) — MIT-licensed Windows semantic hint-navigation reference.
- [Neru](https://github.com/y3owk1n/neru) — MIT-licensed cross-platform hint-navigation reference; its OCR/pixel paths are outside this product scope.
- [Hints](https://github.com/AlfredoSequeida/hints) — GPL-3.0 Linux accessibility-hint reference; review license compatibility before reuse.
- [Mousemaster](https://github.com/petoncle/mousemaster) — useful interaction reference; no repository-level license was identified, so do not reuse its code without clarification.
- [Weston backends](https://wayland.pages.freedesktop.org/weston/toc/running-weston.html) — documents nested Wayland and headless compositor backends for the Linux worker investigation.
- [Power Automate Picture-in-Picture sessions](https://learn.microsoft.com/en-us/power-automate/desktop-flows/run-desktop-flows-pip) — Windows child-session behavior and limitations reference.

## Branch and tracking

- The `v1.0` branch is the isolated development and integration line for this roadmap. Its starting commit is a baseline only; work for this plan does not change `main`.
- Use short-lived branches and pull requests targeting `v1.0` for individual roadmap changes. Do not commit directly to or force-update the long-lived version branch.
- Track individual work through issues and pull requests linked to this roadmap.
- Any later handoff from `v1.0` to `main` requires a separately reviewed version handoff and pull request.
